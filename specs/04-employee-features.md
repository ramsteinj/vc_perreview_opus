# 04. 직원 기능 상세 요구사항

## FR-E-01. 로그인

**성명 + 사번 + 비밀번호**로 로그인한다. 상세 규칙은 [03-auth.md](03-auth.md) 참조.

### 화면 요구사항

- 입력 필드 3개: 성명, 사번, 비밀번호
- 세 필드 모두 필수. 빈 값이면 클라이언트에서 즉시 검증 메시지 표시
- 로그인 실패 시 필드별로 구분하지 않고 폼 상단에 통합 에러 메시지 표시
- 로그인 성공 시 `role`에 따라 분기
  - `EMPLOYEE` → `/my/evaluations`
  - `ADMIN` → `/admin/dashboard`
- 비밀번호 필드는 표시/숨김 토글 제공

### 수용 기준

- [ ] 성명이 등록된 값과 다르면 사번·비밀번호가 맞아도 로그인되지 않는다
- [ ] 비활성(`is_active=False`) 계정은 로그인할 수 없다
- [ ] 5회 연속 실패 시 10분간 차단된다
- [ ] 새로고침해도 로그인 상태가 유지된다 (refresh 토큰)

## FR-E-02. 내 평가 목록 조회

로그인한 사용자가 **평가자로 배정된 대상 목록**을 조회한다.

### 표시 항목

| 컬럼 | 설명 |
|------|------|
| 평가 대상 | 직원명(사번·부서) 또는 부서명 |
| 대상 유형 | 개인 / 부서 |
| 차수 | 1차 / 2차 |
| 진행률 | `0% ~ 100%` 프로그레스 바 |
| 상태 | 미시작 / 임시저장 / 제출완료 |
| 액션 | [평가하기] / [수정] / [보기] |

### 규칙

- 현재 `status=OPEN`인 회차의 배정만 표시한다
- 본인이 `primary_evaluator`인 배정은 `round=PRIMARY`로,
  `secondary_evaluator`인 배정은 `round=SECONDARY`로 각각 한 행씩 표시한다
  (한 사람이 같은 대상의 1차·2차를 겸할 수는 없다 — [02-data-model.md](02-data-model.md) §4.3)
- 마감일(`ends_on`)이 지난 회차는 응답할 수 없고 읽기 전용으로 전환된다
- 목록 상단에 전체 진행 현황 요약 표시: `제출 완료 3 / 전체 7`

### 수용 기준

- [ ] 본인에게 배정되지 않은 대상은 목록에 나타나지 않는다
- [ ] 다른 사용자의 배정을 API로 직접 요청해도 403이 반환된다
- [ ] `DRAFT`/`CLOSED` 회차의 배정은 응답 대상으로 표시되지 않는다

## FR-E-03. 평가 문항 응답

배정된 대상 하나에 대해 평가지를 작성한다.

### 화면 구성

```
┌───────────────────────────────────────────────┐
│ 2026년 상반기 평가 · 1차                        │
│ 평가 대상: 김철수 (20210133 · 개발1팀)          │
│ 마감: 2026-09-30                               │
│ ▓▓▓▓▓▓▓▓░░░░  진행률 67% (2/3)                 │
├───────────────────────────────────────────────┤
│ 1. 업무 성과                    가중치 50%      │
│    업무 목표 달성도와 산출물의 품질을 평가합니다. │
│    ○1  ○2  ○3  ●4  ○5                         │
│    [의견 (선택)                             ]  │
├───────────────────────────────────────────────┤
│ 2. 협업                         가중치 30%      │
│    ○1  ○2  ○3  ○4  ●5                         │
│    [의견 (선택)                             ]  │
├───────────────────────────────────────────────┤
│ 3. 태도                         가중치 20%      │
│    ○1  ○2  ○3  ○4  ○5     ← 미응답            │
│    [의견 (선택)                             ]  │
├───────────────────────────────────────────────┤
│ 종합 의견                                      │
│ [                                          ]  │
├───────────────────────────────────────────────┤
│           [임시 저장]   [제출하기]              │
└───────────────────────────────────────────────┘
```

### 규칙

- 항목은 `order` 오름차순으로 표시한다
- 척도는 `1 ~ item.max_score` (기본 5점 척도)
- **가중치를 화면에 표시한다** — 평가자가 항목의 비중을 인지하고 평가하도록
- 항목별 의견(`comment`)은 선택 입력
- 종합 의견(`overall_comment`)은 선택 입력
- 제출 후에는 읽기 전용으로 표시된다 (수정 불가)

### 수용 기준

- [ ] 모든 활성 항목이 표시된다
- [ ] 비활성(`is_active=False`) 항목은 표시되지 않는다
- [ ] 제출 완료된 평가지는 입력 컨트롤이 모두 비활성화된다
- [ ] 회차가 `CLOSED`면 새 응답을 저장할 수 없다 (409)

## FR-E-04. 임시 저장

작성 중인 응답을 제출하지 않고 보관한다.

### 동작

| 트리거 | 동작 |
|--------|------|
| [임시 저장] 버튼 클릭 | 즉시 저장. 토스트로 "임시 저장되었습니다" 표시 |
| 자동 저장 | 입력 변경 후 **3초 디바운스**로 자동 저장 |
| 페이지 이탈 | 저장되지 않은 변경이 있으면 확인 다이얼로그 표시 |

### 규칙

- 임시 저장 시 `EvaluationResponse.status = DRAFT`를 유지한다
- **부분 저장을 허용한다.** `score`가 비어 있는 항목이 있어도 저장된다
- 저장 API는 **멱등한 upsert**로 동작한다. 같은 평가지를 여러 번 저장해도
  `EvaluationAnswer`가 중복 생성되지 않는다 (`update_or_create`)
- 마지막 저장 시각을 화면에 표시한다: `마지막 저장: 14:32`

### API

```
PUT /api/my/responses/{id}/
{
  "answers": [
    { "item": 1, "score": 4, "comment": "" },
    { "item": 2, "score": 5, "comment": "협업 우수" },
    { "item": 3, "score": null, "comment": "" }
  ],
  "overall_comment": "전반적으로 우수합니다."
}
```

### 수용 기준

- [ ] 임시 저장 후 브라우저를 닫았다 다시 열어도 입력 내용이 복원된다
- [ ] 자동 저장이 입력 중 과도하게 호출되지 않는다 (디바운스 확인)
- [ ] 임시 저장을 10회 반복해도 답변 레코드는 항목당 1건을 유지한다
- [ ] 네트워크 오류 시 저장 실패를 사용자에게 알린다

## FR-E-05. 진행률 표시

### 계산식

```
진행률(%) = (score가 null이 아닌 답변 수 / 활성 항목 총 수) × 100
```

- 소수점 없이 내림 정수로 표시한다
- 항목별 의견은 진행률에 영향을 주지 않는다 (선택 입력이므로)
- 종합 의견도 진행률에 영향을 주지 않는다

### 표시 위치

| 위치 | 형태 |
|------|------|
| 평가 목록 | 행별 프로그레스 바 + `67%` |
| 평가지 작성 화면 상단 | 프로그레스 바 + `67% (2/3)` (sticky) |
| 목록 상단 요약 | `제출 완료 3 / 전체 7` |

### 서버 응답

`EvaluationResponse` 직렬화 시 서버가 계산해서 내려준다.
클라이언트에서도 입력 즉시 낙관적으로 재계산해 반응성을 확보한다.

```json
{
  "id": 12,
  "status": "DRAFT",
  "progress": 67,
  "answered_count": 2,
  "total_items": 3
}
```

### 수용 기준

- [ ] 모든 항목에 점수를 입력하면 100%가 된다
- [ ] 점수를 지우면 진행률이 감소한다
- [ ] 항목이 0개인 예외 상황에서 0으로 나누지 않는다 (진행률 0% 처리)

## FR-E-06. 중복 응답 방지

한 평가자가 같은 대상·같은 차수에 대해 **평가지를 두 번 제출할 수 없다.**

### 방어 계층

| 계층 | 수단 |
|------|------|
| DB | `UniqueConstraint(assignment, round)` on `EvaluationResponse` |
| Service | 제출 시 `status == SUBMITTED`면 거부 |
| API | 제출된 평가지에 대한 `PUT`/`POST` 요청에 409 반환 |
| UI | 제출 완료 항목은 버튼 비활성화, [보기]만 제공 |

### 제출 API

```
POST /api/my/responses/{id}/submit/
```

### 제출 전 검증

1. 회차가 `OPEN` 상태인가 → 아니면 `409 CYCLE_NOT_OPEN`
2. 마감일(`ends_on`)이 지나지 않았는가 → 지났으면 `409 CYCLE_DEADLINE_PASSED`
3. `request.user == response.evaluator`인가 → 아니면 `403`
4. 이미 `SUBMITTED`인가 → 맞으면 `409 ALREADY_SUBMITTED`
5. **모든 활성 항목의 `score`가 채워졌는가** → 아니면 `400 INCOMPLETE_ANSWERS`
   (미입력 항목 ID 목록을 응답에 포함)

### 제출 처리

```python
with transaction.atomic():
    response = EvaluationResponse.objects.select_for_update().get(pk=pk)
    # ... 검증 ...
    response.status = ResponseStatus.SUBMITTED
    response.submitted_at = timezone.now()
    response.save(update_fields=['status', 'submitted_at', 'updated_at'])
```

`select_for_update()`로 동시 제출 요청(더블 클릭, 다중 탭)을 직렬화한다.

### 오류 응답 형식

```json
{
  "code": "ALREADY_SUBMITTED",
  "detail": "이미 제출된 평가입니다. 수정이 필요하면 관리자에게 문의하세요."
}
```

```json
{
  "code": "INCOMPLETE_ANSWERS",
  "detail": "응답하지 않은 항목이 있습니다.",
  "missing_items": [3, 7]
}
```

### 수용 기준

- [ ] 제출 버튼을 빠르게 두 번 클릭해도 평가지가 하나만 제출된다
- [ ] 두 개의 탭에서 동시에 제출해도 하나만 성공하고 나머지는 409를 받는다
- [ ] 제출 완료 후 새로고침하면 읽기 전용 화면이 표시된다
- [ ] 미입력 항목이 있으면 제출이 거부되고 해당 항목으로 스크롤·하이라이트된다
- [ ] 관리자가 반려(`reopen`)하면 다시 수정·제출할 수 있다
